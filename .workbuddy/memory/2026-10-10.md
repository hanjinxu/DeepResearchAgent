## 持久状态：补齐建议
- LangGraph **原生支持 checkpointer**（MemorySaver / SqliteSaver / PostgresSaver），`graph.compile(checkpointer=...)` + `thread_id` 即可，改动极小。
- 结论：**性价比最高的补短板**——把 harness 的「持久状态」从 ❌ 补成 ✅，只需几行；且舆情长任务 + 法务审核场景本身需要断点续跑 / human-in-the-loop（interrupt）。
- **关键区分（面试易被追）**：checkpointer = thread 内状态持久化（断点续跑/多轮/时光回溯）；**≠ 长期记忆**。跨任务知识复用要 `Store`（InMemoryStore / PostgresStore），即此前说的「缺长期记忆」那块。
- LangGraph 覆盖度标准口径（用户认可版）：完全覆盖 workflow/loop + 短期记忆；部分覆盖 tools 抽象 + 持久化接口；完全不覆盖 evaluation + 权限控制。

## 关键业务背景（决定记忆/持久化的取舍）
- **Deep Research Agent 生产形态 = 每天根据 top100 热点 query 生成 100 篇报告**。是**批处理**，不是交互式对话。→ 记忆的定位应重写为「跨任务知识复用 + 成本优化」，而非「对话连续性」。
- 三类记忆分别评估（勿一刀切）：
  1. **当天任务间缓存/去重**（100 个 query 之间话题/实体重叠 → 搜索与摘要结果复用）：**ROI 最高**，直接省 API 成本与时间。
  2. **跨天长期记忆**（同一事件跨天发酵 → 检索历史结论支持「进展追踪」，并让 reward 里的「新颖度」可相对历史计算）：取决于 query 跨天重叠率，舆情事件有生命周期，大概率值得。
  3. **单任务内 checkpointer**（断点续跑）：价值中等，批处理下任务级重试更直接；加它主要是补 harness 亮点的低成本手段。
- 推荐优先级：任务间去重缓存 > 跨天事件记忆 > checkpointer。

## 报告模板结构（长期记忆的现成 schema）
- 舆情报告按**固定模板**填充（用户确认）：
  ① 舆情事件概述（1.1 事件定调 / 1.2 时间线表：时间·节点·来源）
  ② 关键事实梳理（2.1 已确认事实 / 2.2 未确认信息·谣言 / 2.3 信息可信度评估表）
  ③ 法律风险识别（3.1 风险类型+法条 / 3.2 风险等级评估表）
  ④ 法务处置建议（4.1 动作清单 / 4.2 优先级与时效 / 4.3 对外回应策略）
  + 来源列举
- 案例：华为内部推荐政策引员工不满舆情（时间线跨度 2024-06-01~06-14，跨两周）。
- **核心结论**：模板本身 = 长期记忆的天然档案 schema，长期记忆必要性↑、实现难度↓。
  - 1.2 时间线 → 增量追加数组（天然跨天累积，价值最高）
  - 2.1/2.2 → 事实状态机（未确认→已证实/已辟谣，跨天迁移）
  - 2.3 → 信源可信度累积（可形成信源黑白名单）
  - 3.1/3.2 → 风险等级演化轨迹
  - 4.x → 处置动作台账 + 时效追踪
- **事件归并难度被模板化解**：1.1 事件定调 + 时间线首节点（主体/首发时间/核心争议）即事件指纹，精确匹配即可，语义匹配兜底。
- 杀手功能：**每日 Diff / 变化摘要**（对比昨日档案 vs 今日报告：新增时间线 X 条、Y 条传闻已辟谣、风险等级 A→B），报告从「静态快照」升级为「动态追踪」。
- 降本量化：历史时间线/已确认事实不重搜，只搜增量 →预估省 20~40% 搜索调用。

## query 重复判定方案（事件归并落地）
- 分清两层：**query 文本相似** ≠ **事件语义同一**。用户问的是后者。
- **关键洞察**：不要直接比对原始 query 文本，先用模板 1.1「事件定调」（主体 + 核心争议 + 类型）抽成**结构化中间表示**，再与历史档案的定调比对——比比文本准得多（模板白送的 canonical 表示）。
- 分层匹配流水线：
  1. L1 精确匹配：实体词典 + 议题归一化（同义词映射）→ 快、覆盖一部分
  2. L2 向量召回 top-5：embedding 检索（时间窗 90 天）→ 召回好但区分度差（同主体不同事件会误召回）
  3. L3 LLM 精排判定：二分类「是否同一事件」+ 置信度 + 理由 → 最可靠
  4. L4 兜底：未命中则新建档案
- 判据必须显式定义：同主体（必须）+ 同核心争议（必须）+ 时间窗口（舆情跨月，用 90 天）+ **演化关系**（回应/辟谣/反转/处罚 = 同一事件链，非新事件）。
- 【事件链】母事件 + 子事件演化归同一档案的时间线节点，不拆成独立事件。
- 权衡铁律：**误合并比漏合并危险**（污染事实）→ 阈值保守（如 LLM 置信度 >0.8 才合并）。
- 成本：100 query/天 × top-5 = ~500 次 LLM 二分类，用 7B 小模型可控。
- 离线补漏：定期重跑，发现事后判定为同一事件的档案 → 支持合并/分裂操作。

## 增量搜索怎么做（纠正上一轮表述）
- 上一轮"只搜 2.2 未确认信息 + 时间线最新节点"表述不准确，易被误解为两次搜索。
- **正确理解**：「最新节点」不是搜索对象，是**搜索结果里抽取出来的产物**。实际只有**一次增量搜索**，产出两个输出。
- 增量搜索 = **带时间下界**的检索：
  - query = 事件主体 + 核心议题 + 进展类关键词（回应/辟谣/通报/处罚/整改/反转/否认/致歉/热搜…）
  - 时间过滤 = (上次报告日期, 今天) ← **「最新」靠时间下界实现，不是靠关键词**
  - 项目用 Tavily，可用 start_date / end_date 参数
- 搜回来的结果分流：① 能证实/证伪 2.2 传闻的 → 更新事实状态机；② 带新时间点的进展 → 抽成 timeline 新节点。
- 必须做**已知节点去重**（媒体报道会反复引用旧节点），用已有 timeline 时间戳 + 语义比对过滤。
- 进阶：按事件热度动态调搜索强度（冷事件降轮次）——与轮次惩罚/早停机制呼应。

## 方案审查结论（用户整理版的两处结构性错误）
1. **张冠李戴**：20~30% 复用率是「当天 100 query 之间的去重缓存」的收益（纯工程、同日），不是「跨天长期记忆」的收益。两者要分开讲：
   - 当天去重 = 省 20~30% 调用（工程）
   - 跨天记忆 = 省历史节点重搜 + **产品能力（进展追踪/辟谣追踪）**
2. **缺「写回档案」环节**：用户流程只有 读（匹配）→ 搜（增量），没有归档。无写回则档案不增长，长期记忆为空。闭环必须补：命中/新建 → 增量搜 → 分流 → **写回（timeline 追加 / 状态机迁移 / 新档案）** → 下次复用。
3. **L3 不能「取 top1」**：应逐个判定 + 置信度阈值（>0.8 才合并，否则判新事件），并输出 relation（延续/回应/辟谣/反转）用于决定节点如何入 timeline。硬取 top1 会导致误合并。
4. L2 向量召回需带时间窗（90 天）。

## 存储方案（最终定稿：极简 + 向量）
- **核心原则：档案 = 报告本身**。模板已固化结构（时间线/事实/风险/处置都在报告里），不要把这些再抽成独立字段存一遍——用户明确指出我此前的 nested 字段 + 双 index + 乐观锁是过度设计。
- 一个 index，**6 个字段**：`event_id`(指纹 subject|issue) / `subject` / `issue` / `report_date` / `content`(报告全文, `index:false`) / `embedding`(dense_vector dims=1024, cosine)。
- **append-only**：每天一份报告，不更新 → 无需乐观锁、无并发冲突、无需第二个 index。
- **embedding 编码对象 = 事件定调**（subject + issue + 报告 1.1 概述段），不是报告全文。
- 匹配流程：指纹精确匹配 → 向量 kNN 兜底（`filter: report_date >= now-90d`）→ LLM 裁决（置信度 >0.8 才合并）。
- 加向量后的坑：同一事件 N 份报告 → 向量近乎重复 → kNN 后必须**按 event_id 去重取最新**，`num_candidates` 开 50~100 保证多样性。
- 复杂度回加条件：某 subject 下候选 > 几十条才需向量召回；要跨事件全局统计时才把结构化字段独立出来。当前都不需要。
- 早期记录的 pgvector / ES 双 index 方案已作废。

## 并发写入结论
- ES 单文档写入本身原子，不会写坏；冲突与否**取决于 `_id`**：① 自动 _id → 不冲突但产生重复文档；② `_id=event_id` → 并发覆盖丢数据 ❌；③ `_id=event_id+report_date` → 天然幂等，冲突返回 409 可处理 ✅。
- **真正的坑不是写冲突，是竞态重复建档**：两个并发 query 同时匹配不到历史 → 各自新建 → 同一事件产出两份报告。
- **根治方案：两阶段**——先对当天 100 个 query 做批量归并（当天内部聚类 + 与历史匹配）得到 N 个事件任务，再对 N 个任务并发研究。批处理架构天然适配；顺带解决"当天 query 间去重"，省成本。
- 兜底：写入用 `op_type=create`（冲突即忽略并记日志），查询时按 event_id 去重取最新。

## 权限控制判断（本项目）
- 结论：**需要，但要的是「Agent 运行时护栏」，不是「用户权限系统（RBAC/多租户/审批流）」**——后者对单团队内部、无人值守批处理是过度设计。
- 三个特性使护栏必要：① 无人值守（每天自动 100 篇，没人盯着）② 要读外部网页内容 ③ 输出交给法务（有法律后果）。
- 风险优先级：
  1. **P0 间接 Prompt Injection**：搜索结果可能被投毒（SEO 污染/竞品抹黑）→ 诱导越权或污染报告。舆情场景尤其真实。
  2. **P0 成本熔断**：100 篇 × 多轮搜索，某篇死循环会失控烧钱 → 单任务轮次/token 上限、单日预算。
  3. **P1 工具白名单/最小权限**：只读工具集；`red_team_agent` 写 md 文件是已有小口子，应限定目录；禁任意 URL 抓取（防 SSRF）。
  4. **P1 输出合规 gate**：报告发布前校验（未证实信息是否标注、是否有诽谤性表述）。
- **已具备的雏形**：红队对抗审查（可扩展职责为安全审查，检查注入指令/恶意信源）+ 搜索 API 的无效链接过滤。
