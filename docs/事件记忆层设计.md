# 事件记忆层设计（判重 · 进展追踪 · 辟谣追踪）

> 一句话：**让"同一个热点事件第二天再来一次"不再从零调研**——判重命中后只做增量进展检索，
> 把结果归位到报告的「1.2 时间线」和「2.2 事实状态机」，并把事件档案累积回写入库。

---

## 1. 它解决了什么问题

产品侧的触发方式是：**每天由热点事件模型识别出 Top-150 热点，逐个送进 Deep Research 流水线出报告**。

在这个量级下，最刺眼的浪费是**重复**：一个热点事件往往连续数天霸榜（微博热搜的平均生命周期就是 3~7 天），
但流水线对第 2 天、第 3 天的同一条事件完全无感知——重新拆子 Query、重新起并行子 Agent、
重新全量搜索、重新去噪、重新红队审查，最后生成一份 90% 内容与昨天雷同的报告。

记忆层就是在这个位置插入的一道闸门：

- **省成本**：命中历史事件 → 不再重搜已知的历史节点；
- **加能力**（比省成本更值钱）：同一事件的多次报告被归并成一条**持续生长**的档案，
  于是「进展追踪」和「辟谣追踪」这两个产品能力自然涌现。

## 3. 三级判重：为什么是漏斗而不是"直接上向量/上 LLM"

判重是**高精度优先**的问题。错误合并（把两个不同事件当成一个）会把不相干的历史基线
灌进当前报告的上下文，污染比"没合并"严重得多。所以设计成逐级昂贵的漏斗：

### L1 精确匹配（成本 0）
实体 + 议题归一化后完全一致 → 直接命中，**不调模型**。
覆盖"每天重复触发同一个热点"这个主场景（占绝大多数请求）。

归一化做的事：去标点、去空白（含全角）、小写化、剥离舆情体裁词与时效词——
`最新 / 进展 / 动态 / 回应 / 声明 / 事件 / 风波 / 舆情 / 热搜 …`。

> 这样「余承东 竹知了 最新回应」和「余承东竹知了事件」会归一到同一个 key「余承东竹知了」。

命中条件（两者都满足）：主体一致（相等 / 互为子串 / 命中别名）+ 议题一致（相等，或双方都 ≥4 字时互为子串）。

### L2 向量召回 top5（成本 1 次向量计算）
字面不同但语义相近（换了说法、加了"最新回应"）。**只负责粗筛候选，不做判定**。

### L3 LLM 判定（成本 1 次 LLM 调用）
只在前两级都没结论时才走。在候选里做最终判定，输出 `event_id + confidence + reason`。
prompt 里明确写着：**拿不准时倾向判否**（宁可新开一条，不要错误合并）。

### ⚠️ 阈值标定：L2 的分数只能排序，不能判定

这是实测出来的坑，写进了代码注释和回归测试：

| 关系 | hashing-ngram 余弦 |
|---|---|
| 同事件 · 换说法 | **0.35** |
| 同事件 · 长报告正文 / 摘要 | **0.18 ~ 0.27** |
| 同事件 · 短标题（字面重叠少） | **0.10** |
| 相关但不同事件（同主体不同议题） | **0.07** |
| 完全无关 / 议题不同 | **−0.07 ~ −0.04** |

**同事件的低分（0.10）与不同事件的高分（0.07）几乎贴在一起。**
所以：

- `l2_floor` 默认取 **0.05**（hashing-ngram）/ **0.55**（真 embedding），职责仅是"过滤明显无关与负相关"；
- **判定必须交给 L3**；
- 如果谁凭直觉把 floor 调到 0.15，正确答案会被一起过滤掉、L2 永不触发——
  `test_event_memory.py` 里有一条专门的回归断言拦这个改动。

## 4. 增量进展追踪：「时间 + 关键词」检索

命中历史事件后，用一组领域词典化的检索式去问"这件事最新发生了什么"：

```
华为 内部推荐政策 最新进展 2026年10月      ← 时间锚定式
华为 内部推荐政策 2026年10月               ← 时间锚定式
华为 内部推荐政策 回应 声明 辟谣           ← 关键词组 1
华为 内部推荐政策 通报 处罚 整改           ← 关键词组 2
华为 内部推荐政策 起诉 反转 否认           ← 关键词组 3
华为 内部推荐政策 致歉 热搜                ← 关键词组 4
```

**为什么是这 11 个关键词**：
`回应 声明 辟谣 通报 处罚 整改 起诉 反转 否认 致歉 热搜`

舆情事件的**实质进展**基本只发生在这几类动作上。用它们做检索式，相当于给"最新进展"
这个模糊概念装了一个**领域词典化的锚点**——比单搜"最新消息"命中率高得多。
11 个词按 3 个一组排布，恰好填满 `max_queries=6` 的预算。

**成本控制**：增量检索**不走**主链路那套"网页全文 LLM 摘要"管线（每条 URL 一次 LLM 调用），
而是直接取 Tavily 返回的标题 + 摘要片段（已截断 800 字）。
理由：增量追踪只需判断"有没有新事实"，不需要长文摘要。于是 6 条检索式 ≈ **0 次摘要调用**。

## 5. 结果归位：两个槽位

检索回来的东西不能一股脑塞进报告，按性质分流：

| 内容性质 | 归到哪 | 数据操作 |
|---|---|---|
| 能证实/证伪某条传闻（"官方否认""当事人承认"） | **②2.2 事实状态机** | `unconfirmed → confirmed / refuted / partially_confirmed`，并**追加一条迁移历史** |
| 带新时间点的事件进展（"6-15 华为发布邮件回应"） | **①1.2 时间线** | 按 `(time, node)` 指纹去重后追加，新节点标 `is_new` |
| 基线里没有的全新传闻 | **②2.2** | 以 `unconfirmed` 状态新建条目 |

### 状态机的关键设计：只迁移，不覆盖

```
RumorState
  rumor_id     : 由传闻文本归一化后哈希 → 跨报告稳定，保证能定位到同一条
  text         : 传闻原文
  status       : unconfirmed | confirmed | refuted | partially_confirmed
  confidence   : 低 / 中 / 高
  evidence     : [来源 URL / 引文]
  history      : [{date, from, to, reason, evidence}]   ← 迁移审计链
  first_seen / updated_at
```

`history` 是**辟谣追踪**能力的载具：报告里可以直接展示
"该传闻 09-01 首次出现（未确认）→ 10-12 被官方书面否认（已证伪）"。

LLM 定位历史传闻用的是「归一化 + `difflib` 模糊匹配」：
LLM 回填的 `target` 只要与基线文本基本一致就能命中；匹配不上的按全新传闻处理。

## 6. 存储：Schema 与后端

### 落库文档

```json
{
  "event_id": "华为|内部推荐政策",
  "subject": "华为",
  "issue": "内部推荐政策",
  "report_date": "2026-10-12",
  "content": "……本次报告全文……",
  "embedding": [/* 256 dims */],

  "timeline":  [{"time": "2026-10-05", "node": "华为发布内部邮件回应", "source": "cls.cn", "is_new": true, "first_seen": "2026-10-12"}],
  "rumors":    [{"rumor_id": "rmr_a792834469f6", "text": "内部推荐存在利益输送", "status": "refuted",
                 "confidence": "高", "evidence": ["https://..."],
                 "history": [{"date": "2026-10-12", "from": "unconfirmed", "to": "refuted",
                              "reason": "官方邮件明确否认", "evidence": "https://..."}]}],
  "delta_log": [{"date": "2026-10-12", "summary": "...", "queries": [...],
                 "timeline_added": 1, "rumor_transitions": 1}],
  "aliases": ["华为", "内推"],
  "first_seen": "2026-09-01",
  "last_seen": "2026-10-12",
  "report_count": 2,
  "content_archive": [{"report_date": "2026-09-01", "content": "……上一版报告……"}],
  "meta": {"embedding_provider": "hashing-ngram", "embedding_dim": 256, "store_backend": "jsonl"}
}
```

前 6 个字段是约定的最小 schema，其余为事件追踪扩展。

### 两种后端，ES **不是**硬依赖

```
config.yml → event_memory.store.backend: jsonl | elasticsearch
```

| 后端 | 依赖 | 说明 |
|---|---|---|
| `jsonl`（默认） | 零依赖 | 追加式，last-write-wins，按 `event_id` 去重 |
| `elasticsearch` | `pip install elasticsearch` | 建 `dense_vector` + keyword/text mapping；**连接失败或维度未知时自动降级 JSONL 并告警** |

这个降级不是"容错彩蛋"，是必须的：AutoDL 上通常没有 ES，
而**记忆层是增值能力、不是必要链路**——它绝不能把已经跑通的研究主链路拖挂。
两个节点全部包在 `try/except` 里，任何异常（记忆库宕机、embedding 服务不通、LLM 抽取超时）
都只降级为"无历史"，研究照常进行。

## 7. 四种运行路径的成本 / 质量取舍

| 路径 | 触发条件 | LLM 调用 | 搜索调用 | 报告质量保障 |
|---|---|---|---|---|
| **新事件** | L1/L2/L3 均未命中 | 完整链路（拆子Query + 3×ReAct researcher×5~15轮 + 去噪 + 红队 + 评分，可能多轮迭代） | 15~45 | 全流程 |
| **命中 · full**（默认） | 命中历史事件 | 完整链路 **+ 3~4 次**（判重 1~2 + delta 抽取 1 + 归档 1） | 完整 **+ 6** | 全流程（但研究范围收敛到"只补新进展"） |
| **命中 · fast** | 命中 + `increment_mode: fast` | **约 5~6 次**（判重 1~2 + delta 1 + 草稿 1 + 终稿 1 + 归档 1） | **6** | ⚠️ 不经红队与评分迭代 |
| **关闭记忆层** | `enabled: false` | 与改动前完全一致 | — | 全流程 |

**怎么选**：
- `full` —— 省的是**研究范围**（简报明确禁止重梳理已知时间线），报告仍经对抗审查。适合正式出报告。
- `fast` —— 省的是**整条主循环**。适合"只想知道今天有没有新进展"的日常巡检。
  代价是本次报告没有经过红队批评与评分迭代，**这是拿质量换成本**，不是免费的。

## 8. 配置速查

```yaml
event_memory:
  enabled: true
  increment_mode: full        # full | fast

  store:
    backend: jsonl            # jsonl | elasticsearch
    jsonl_path: ./data/event_memory/events.jsonl
    archive_keep: 5
    elasticsearch: {hosts: ["http://localhost:9200"], index: deepresearch_events}

  embedding:
    provider: hashing_ngram   # hashing_ngram | openai_compatible
    dim: 256                  # 仅 hashing_ngram 需要
    openai_compatible: {base_url: http://localhost:8002/v1, model: Qwen3-Embedding-0.6B, dim: 0}

  dedup:
    l2_top_k: 5
    # l2_floor: 留空 = 按 embedder 自动取值（hashing 0.05 / 真 embedding 0.55）
    l3_enabled: true
    candidate_limit: 2000

  delta:
    keywords: [回应, 声明, 辟谣, 通报, 处罚, 整改, 起诉, 反转, 否认, 致歉, 热搜]
    keywords_per_query: 3
    lookback_days: 7
    max_queries: 6
    max_results: 3
    topic: news
```

**关于 embedding**：DeepSeek 官方 API **不提供 embedding 接口**，不能沿用 LLM 的 backend 配置。
默认的 `hashing_ngram` 是"字符 2/3-gram + hashing trick 映射到 256 维 + L2 归一化"，
零依赖、离线可跑、固定维度可直接落 ES 的 `dense_vector`。
要更好的语义召回，把它切到 `openai_compatible`，指向本地 vLLM 部署的 `Qwen3-Embedding-0.6B` 即可。

## 10. 面试讲述要点

### 30 秒版

> 我们的触发方式是每天 150 个热点事件进流水线，但热点平均生命周期 3~7 天，
> 同一事件第 2、3 天再来一遍会重复做全量调研。所以我加了一层**事件级记忆**：
> 用「实体+议题精确匹配 → 向量召回 top5 → LLM 判定」三级漏斗判重，
> 命中后不再重搜历史节点，只用「时间+11 个动作关键词」检索最新进展，
> 结果分流到两处——能证实/证伪传闻的进「2.2 事实状态机」，带新时间点的进「1.2 时间线」，
> 最后把事件档案累积回写存储。

### 三个最容易被追问的点

**Q1：为什么三级？直接上向量检索不行吗？**
> 不行。判重是**高精度优先**的问题——错误合并会把不相干的历史基线灌进当前报告，
> 比漏合并严重得多。而且我实测过 hashing-ngram 的余弦量纲：同事件的短标题是 0.10，
> 同主体不同议题是 0.07，**几乎贴在一起**。所以向量分数只能用来排序，
> 不能用来判定，必须有 LLM 兜底。L1 则负责吃掉"每天重复同一个热点"这个主场景的绝大部分请求，零模型成本。

**Q2：为什么阈值定 0.05 而不是常见的 0.8？**
> 因为量纲不同。0.8 是**真 embedding** 的经验值，同事件通常 0.85+。
> 我用的是零依赖的 hashing-ngram（字符 2/3-gram 哈希到 256 维），
> 绝对余弦天然低得多。我把实测标定表写进了代码注释，还加了一条回归断言——
> 谁把 floor 调到 0.15 以上、导致正确候选被误杀，测试会直接挂。这是防止后人凭直觉改参数。

**Q3：你说的"省"到底省在哪？**
> 分两级。
> 一是**省研究范围**：命中后注入的简报明确写了「不要重新梳理已在已知时间线里的事实」，
> 把研究焦点收敛到三类增量。
> 二是 **fast 模式直接跳过整条主循环**——不拆子 Query、不起并行子 agent、不去噪、不走红队评分。
> 但这里是**有代价的**：fast 模式下报告不经对抗审查，质量保障弱于 full。
> 所以我把它做成配置开关而不是默认行为——**省成本和保质量是 trade-off，不该由我一个人拍板**。

**Q4：ES 挂了怎么办？**
> 自动降级到本地 JSONL 并告警。记忆层是增值能力不是必要链路，
> 两个节点全部 try/except 包裹，任何异常都降级为"无历史"，研究流程照常走完。
> 这一点我在集成测试里专门验了：模拟记忆库宕机，图仍然正常流转到报告产出。
